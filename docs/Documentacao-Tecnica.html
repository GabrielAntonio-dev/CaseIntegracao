Case Integração — Sistema de Pedidos → CRM

Projeto: CaseIntegracao · Stack: C# / ASP.NET Core (.NET 9)
Estrutura: Api + Core + Tests · Persistência: arquivo JSON
Documento complementar ao README (visão aprofundada)

1. Objetivo e contexto

O serviço atua como integrador entre dois sistemas:

  • Sistema de Pedidos — dispara webhooks quando um pedido é criado, atualizado ou cancelado.
  • CRM — mantém clientes e pedidos via API REST (neste projeto, um mock embutido no mesmo host).

O integrador recebe o evento, garante o cliente no CRM, sincroniza o pedido e trata problemas típicos de integração: eventos fora de ordem, falhas temporárias na API de destino e reenvios duplicados.

2. Escopo funcional

  1. Endpoint HTTP para receber o webhook do sistema de pedidos.
  2. Se o cliente não existir no CRM, criá-lo antes de sincronizar o pedido.
  3. Criar ou atualizar o pedido no CRM conforme o tipo de evento.
  4. Idempotência por eventId.
  5. Ordenação por occurredAt (estado final = mais recente).
  6. Retry sensato em falhas 5xx, 429 e timeout, sem perder o evento.

Diferenciais mantidos: exponential backoff, circuit breaker (Polly), métricas de sincronização e reflexão sobre escala com fila.

5. Lógica de negócio detalhada

5.1 Recepção do webhook

  1. WebhooksController recebe o JSON; se eventId estiver vazio, usa X-Idempotency-Key.
  2. WebhookMapper converte o contrato inglês em entidades de domínio.
  3. Em order.canceled, o status vira Cancelado automaticamente.
  4. EventoPedidoProcessor.ReceberAsync executa o pipeline.

5.2 Idempotência

Se já existe evento com o mesmo eventId em Sincronizado ou IgnoradoObsoleto, a API responde alreadyProcessed: true e não chama o CRM novamente. Cada evento de negócio novo (create → update → cancel) precisa de um eventId distinto.

5.3 Ordenação de eventos

PoliticaOrdenacaoEventos compara occurredAt com ProjecaoPedido.LastOccurredAt: evento mais antigo → IgnoradoObsoleto; mais novo ou igual → aplica no CRM e na projeção.

5.4 Sincronização com o CRM

  1. GarantirClienteAsync — GET; se 404, POST; se existe, PUT.
  2. UpsertPedidoAsync — GET; se 404, POST; senão PUT. Status enviado em inglês (pending/confirmed/canceled).

5.5 Tratamento de falhas e retry

Polly (HttpClient): retries curtos para 429/5xx + circuit breaker (5 falhas → abre 15s).

Aplicação: falha transitória → Falhou + backoff exponencial com jitter; RetryBackgroundService reprocessa; após MaxAttempts → CartaMortua.

CRM mock falha ~15% (CrmMock:FailureRate): 429, 500 ou timeout real (delay padrão 12s > timeout do client 10s).

12. Escala com fila (reflexão)

Em produção, o webhook validaria o payload, gravaria um inbox e publicaria em fila (SQS, RabbitMQ ou Azure Service Bus). Workers competiriam com visibility timeout e DLQ. Idempotência e projeção ficariam em store compartilhado (banco), permitindo múltiplas instâncias.

13. O que mudaria com mais tempo

  • Banco (ou outbox/inbox) em vez de arquivo
  • Testes de integração com WebApplicationFactory
  • Assinatura HMAC no webhook
  • OpenTelemetry / tracing
  • Exemplos OpenAPI por eventType
